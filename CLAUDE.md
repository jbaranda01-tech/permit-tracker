# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

PermitTracker is a permit/certification tracking system for LB Caribe Services and Professional Logistics (PLI). It tracks employee permits (NTSP, TWIC, medical certs, etc.) and equipment permits (marbete, seguro, inspección) with expiration alerts. It also includes a truck issue reporting module where drivers report problems via link-based access and shop staff triage/resolve them. The UI is in Spanish.

## Commands

```bash
# Local development
python app.py                    # Runs on http://localhost:5000

# Environment variables needed
export SECRET_KEY=dev-secret
export DATABASE_URL=sqlite:///permits.db   # SQLite for local dev; production uses DATABASE_PRIVATE_URL (Railway internal network)

# Database
flask init-db                    # Creates tables + default admin user (admin/admin123)
flask db migrate -m "message"    # Generate migration (Flask-Migrate, but no migrations dir yet)
flask db upgrade                 # Apply migrations
flask dedup --dry-run            # Preview duplicate cleanup
flask dedup                      # Remove duplicate employees/permits/equipment (vehicles)/issue reports
flask migrate-shared-insurance --dry-run    # (historical) Preview moving per-vehicle SEGURO into shared CompanyPermit
flask migrate-shared-insurance              # (historical) Pre-fill LB/PLI shared insurance, hide per-vehicle copies
flask migrate-class-insurance --dry-run     # Preview splitting shared SEGURO into 4 per-class policies
flask migrate-class-insurance               # SEGURO → SEGURO_TRUCK rename + create CHASSIS/TANK/GENERATOR slots (idempotent)
flask reclassify-equipment --dry-run        # Preview re-running the equipment classifier (model text → class)
flask reclassify-equipment                  # Recompute equipment_class for all non-archived equipment (overwrites manual edits)
flask migrate-issue-statuses --dry-run      # Preview merging the retired issue statuses (en_revision/en_reparacion → en_proceso, resuelto → cerrado)
flask migrate-issue-statuses                # Apply it (also runs automatically on every boot; idempotent)
flask merge-hm-permits --dry-run            # Preview folding each employee's HM-232 permit into the merged HM-126 slot
flask merge-hm-permits                      # Apply it; pairs with distinct dates/documents are reported, not merged (idempotent)
flask send-notifications --dry-run          # Preview without sending emails
flask send-notifications                    # Send all pending notifications
flask send-notifications --employee-id 42   # Single employee (testing)
flask generate-token <employee_id>          # Generate issue-reporting access link for a driver
flask assign-issue-role <username> shop     # Assign shop role for issue module

# Production (Railway)
gunicorn app:app --bind 0.0.0.0:$PORT --workers 2 --timeout 120 --preload
```

## Architecture

**Flask app with one Blueprint** — permit routes in `app.py`, issue reporting in the `issues/` Blueprint:

- `app.py` (~2970 lines): All permit routes, CLI commands, Excel import logic, PDF + Excel report generation, file upload handling, email notification helpers. Contains role decorators (`@admin_required`, `@manager_required`) and context processors: one injects `today` and `alert_date` (the 30-day alert-window boundary, consumed by `report_pdf.html` and `employee.html`) into every template, another provides `versioned_static()` for cache-busted asset URLs. Jinja filters: `format_phone`, and `time_ago` (Spanish relative time — "hace 5m / hace 3h / ayer / hace 3d", falling back to `mm/dd/yyyy` beyond ~7 days; computed against `datetime.utcnow()` since issue timestamps are naive UTC; used in the issue queue rows). Registers the `issues` Blueprint. Uses `flask-compress` for gzip/brotli compression. Serves `/manifest.json` for PWA support. Static assets get `Cache-Control: public, max-age=604800` headers.
- `issues/` (Blueprint): Truck issue reporting module. `__init__.py` defines `issues_bp` with `/issues` prefix. `routes.py` has driver report flow, truck-profile shop queue, issue detail, and status update routes. `SEVERITY_RANK` dict, `QUEUE_SORTS` whitelist, and `build_truck_profiles()` helper power the queue's truck-centric grouping and its sort select; `reportable_equipment_list()` is the natural-unit-order wrapper every truck list renders from (see Equipment filtering). `decorators.py` has `@shop_required` (admin auto-grants access) and `@shop_manager_required` (admin OR base-role `manager` + shop role — gates manual report creation).
- `models.py`: SQLAlchemy models — `User`, `Employee`, `EmployeePermit`, `Equipment`, `EquipmentPermit`, `CompanyPermit`, `FileStorage`, `NotificationLog`, `Issue`, `IssueStatusHistory`, `IssuePhoto`, `UserIssueRole`. Permit types and issue constants (categories, severities, statuses) are defined as module-level lists, alongside the equipment-class vocabulary (`EQUIPMENT_CLASSES`, `classify_equipment()`) and the insurance-class maps (`INSURANCE_TYPE_BY_CLASS`, `INSURANCE_CARD_TITLES`). Status logic (expired/expiring_soon/valid/missing/na) lives in model `@property` methods. `NotificationLog` tracks sent email notifications with 7-day dedup. `FileStorage` stores uploaded files as binary blobs in the DB (used alongside the filesystem `uploads/` directory).
- `config.py`: Single `Config` class. Prefers `DATABASE_PRIVATE_URL` (Railway internal network) over `DATABASE_URL`, falling back to SQLite for local dev. Auto-converts Railway's `postgres://` to `postgresql://`. Sets PostgreSQL connection timeout only when using PostgreSQL. `PERMANENT_SESSION_LIFETIME` is 30 days, which is what makes sticky list preferences outlive the browser window. Email notification config: `SENDGRID_API_KEY`, `SENDGRID_FROM_EMAIL`, `ENABLE_SCHEDULER`, `NOTIFICATION_DAY`, `NOTIFICATION_HOUR`.
- `list_prefs.py`: Sticky list preferences — remembers each user's filter/sort choices per list in the Flask session so they survive navigation. Imported by both `app.py` and `issues/routes.py` (it is its own module because `issues/routes.py` cannot import from `app.py` — circular). See the Sticky list preferences note below.

**Two-company model**: Every employee and equipment record has a `company` field (`LB` or `PLI`). The dashboard shows both side by side (the toolbar's company select can narrow to one — non-matching panels are hidden and the lone remaining panel expands to full width via `.company-panel:only-child { grid-column: 1 / -1 }` in `style.css`).

**Equipment classification (`equipment_class`)**: Every `Equipment` row carries an `equipment_class` column — `truck | chassis | tank | generator` (Spanish labels via `EQUIPMENT_CLASSES` + `Equipment.equipment_class_label`, default 'Camión'). `classify_equipment(model, equipment_type=None)` in `models.py` infers the class from the free-text `model` (chasis/carretón → chassis, tanque → tank, generador → generator, anything else → **truck**); the boot block backfills NULL-class rows automatically and `flask reclassify-equipment` re-runs it on demand (note: overwrites manual class edits). All write paths set it: `equipment_new`/`equipment_edit` via a validated "Clase" form select (`_resolve_equipment_class`; the old `equipment_type` Tipo select was removed from `equipment_form.html` — the column survives but is UI-dead), the Excel equipment import (recomputed on update), and the driver `vehicle_create`. The issue module's reportable set is now **class-based**: `reportable_equipment_query` / `_unreportable_reason` filter on `equipment_class == 'truck'` (with an OR-NULL guard + the old `EXCLUDED_EQUIPMENT_MODELS` model-string loop kept only as a NULL-class fallback), and `vehicle_create` rejects non-truck models. The Equipos dashboard has an `equipment_class` filter select ("Todas las clases", `{% if view == 'equipment' %}`), cross-preserved with all other params via the `... or none` idiom. Display sites (`equipment.html` header tag, `report_pdf.html` Tipo column, Excel export Clase column) all use `equipment_class_label`.


**Merging two permit types (`HM-126` + `HM-232` → one `HM126`, 2026-09-02)**: HM-126 and HM-232 are one certification in practice — one document, one expiration — so they were collapsed into a single slot. A merge is the retirement above *plus* a keeper, and it takes the same coordinated edit: `EMPLOYEE_PERMIT_TYPES` keeps `('HM126', 'HM-126 / HM-232')` and drops the `HM232` tuple (the code stays `HM126` so existing rows and their `FileStorage` blobs never move); `report_pdf.html` needs **four** matching edits (a `<th>` pair → one `<th>` and a `'HM232'` dropped from the hardcoded ptype list, in **both** the LB and PLI blocks — the `<th>` count and the loop length must stay equal or the table skews); `employee_permit_new` gained the allowlist guard the equipment side already had. `export_excel`'s Empleados sheet, `employee.html`, `dashboard.html`, `_gather_expiring_items`, `employee_new` and `employee_detail`'s write-on-read backfill all derive from the list and needed nothing — but note that dropping the code from the list is precisely what stops that backfill from re-creating `HM232` rows on every profile view.

Two things make this a *merge* rather than a retirement. (1) **The employee importer is positional** (unlike the header-driven equipment one), and the sheet keeps both columns, so `EMPLOYEE_PERMIT_COLUMNS` (`app.py`, above `EQUIPMENT_COLUMN_ALIASES` — one constant, replacing the map that was duplicated verbatim in both branches of `import_data`) maps **13 and 14 both to `'HM126'`**. Pointing two columns at one code naively would `db.session.add` two rows with the same `(employee_id, 'HM126')` and trip `uq_employee_permit_type`, so `_resolve_employee_permits(row)` collapses the cells *before* any write, by the precedence **a real date (the later of two) > an explicit `N/A` > a blank cell**; `_employee_permit_cell()` holds the unchanged per-cell parsing. (2) **Legacy rows are preserved, not deleted**: `flask merge-hm-permits [--dry-run]` folds `HM232` into `HM126` only where unambiguous (no keeper ⇒ rename in place; blank keeper — the common case, since the backfill already made empty `N/A` slots — ⇒ move the fields across; a blank `HM232` beside a real `HM126`, equally common, ⇒ drop it; identical date and document ⇒ drop the copy), and **leaves a pair with genuinely distinct dates or two distinct documents alone**, listing it under `Conflictos`. `delete_stored_file()` is never called: a blob is either transferred to the keeper or shared with it. Those survivors need `LEGACY_EMPLOYEE_PERMIT_TYPES` (`models.py`, beside the main list): `EmployeePermit.display_name` falls through to it so they render as "HM-232 (legado)" rather than the bare code, and `_legacy_employee_permit_types()` (`app.py`, a `distinct()` query above `_exp_month_options`) keeps them reachable from the dashboard `permit_type` select and gives them an Excel column — **only while such rows exist**, so both disappear on their own once the last one is merged. `_permit_type_status` returns **`'na'`, not `'missing'`, for an absent legacy row** — the usual "an absent row counts as missing" rule would otherwise report the entire roster as needing a retired permit, which is backwards. Legacy rows deliberately get **no** PDF column (that would undo the visual point of the merge); they show on the employee page, in Excel and via the filter. Run `flask merge-hm-permits` once per environment after deploy.

**Permit status system**: 30-day window for "expiring soon" alerts (configured via `Config.ALERT_DAYS_BEFORE`). Status is computed at query time in model properties, not stored. N/A permits are filtered out of profile views — detail routes split permits into `active_permits` and `hidden_permits`. Managers can toggle applicability via dedicated `/toggle` endpoints. Toggling to N/A clears the expiration date.

**Retiring a permit type**: the vocabulary lives in `EQUIPMENT_PERMIT_TYPES` / `EMPLOYEE_PERMIT_TYPES` / `COMPANY_PERMIT_TYPES` (`models.py`), but **deleting a tuple from one of those lists is never enough** — `permit_type` is a plain string column with no FK, enum or check constraint, and several call sites hardcode the code independently of the list. Retiring an equipment-side type takes a coordinated edit across all of them: the list itself; `EQUIPMENT_COLUMN_ALIASES`, the importer's `for ptype in ('MARBETE', 'INSPECCION', 'NTSP')` tuple, and any per-type N/A rule on both `import_equipment` paths; the default permit-slot loop in `equipment_new`; the Excel export's Equipos sheet (its cells are written by **fixed column index**, so dropping one means renumbering every column after it *and* trimming both the header and width lists — the change most likely to go wrong); and `templates/import.html`'s documented column list. (`report_pdf.html` enumerates its own `['MARBETE', 'SEGURO', 'INSPECCION']` list, so check it too.) Left half-done, orphaned rows keep rendering (as the bare code — `EquipmentPermit.display_name` falls back to `permit_type` when the list has no match), keep counting toward the dashboard alert tiles with no filter that can reach them, and get **recreated by the next Excel import**. Two things finish the job: `equipment_permit_new` validates the posted `permit_type` against the current list and falls back to `'OTHER'`, so a stale open tab can't mint a retired type; and a **one-shot `flask` cleanup command** hard-deletes the surviving rows together with their attached documents (`delete_stored_file()` on `file_path` — uploads are `FileStorage` blobs, not files on disk), run once per environment after deploy and then deleted along with the type. Such a command is deliberately **not** `@protect_uploaded_files()`-decorated (same reasoning as `flask dedup`: the guard exists to stop *imports* from touching documents, and would raise `ProtectedFileError` here).

**Dashboard sorting & filtering (Empleados/Equipos views)**: server-side via GET params on `dashboard()` (`app.py`), all cross-preserved by every control (tiles, selects, search form hidden inputs) using the queue's `... or none` idiom. Params: `sort` (`name` default — employees by `name`, equipment by `display_name`/unit # — plus `category` = employees by `Employee.area` / equipment by `Equipment.model` (case-insensitive, blanks last, name tiebreak; the select option label switches "Área"/"Modelo" per view like the `name` option does; deliberately the free-text `model`, NOT `equipment_class` — the class has its own dedicated filter select), `urgency` = expired > expiring > missing > rest, and `expiration` = soonest `next_expiration` first, none-upcoming last — **except when `permit_type` is active**: then `_sort_dashboard_items` sorts by THAT type's own `expiration_date` (or `license_expiration` for `LICENCIA`), ascending, so already-expired dates come first and N/A/missing land last via `date.max`; e.g. `?view=equipment&permit_type=MARBETE&sort=expiration` = marbete by expiration), `permit_type` (a code from the view's type list, plus a `LICENCIA` pseudo-type on Empleados computed from `Employee.license_expiration`), `equipment_class` (Equipos only — SQL filter, see the Equipment classification note), `permit_status` (`expired`/`expiring` — deliberately NOT `status`, which remains the record-status param), `exp_month` (`YYYY-MM`; a "Mes de vencimiento" select of month+year options from `_exp_month_options(view)` — **data-driven**: every month that has at least one counted expiration for the current view (per-entity permits of non-archived owners with non-N/A applicability, plus `license_expiration` on Empleados — the same sources `_expires_in_month` counts, so options and filter can't disagree), sorted chronologically, Spanish labels from the module-level `SPANISH_MONTHS` tuple; Empleados/Equipos only, Empresa ignores it and skips the queries), and `company` (select UI; non-matching panels are hidden entirely, not shown empty — the single visible panel goes full-width via the `:only-child` grid rule; queue.html/archive.html always render two panels so they're unaffected). The whole normalize → query → filter → sort pipeline lives in **`_dashboard_context(args, view=None)`** (above `dashboard()`), which returns the render kwargs plus a `nav_args` dict; `dashboard()` is a thin `render_template('dashboard.html', **_dashboard_context(request.args))` (the `company` view still returns early from the route). It is shared with `_sibling_nav()` so the detail pages' prev/next arrows walk exactly the sequence the dashboard rendered — see the record-to-record navigation note. Because permit status is a computed property (not a SQL column), the SQL queries have **no `order_by`** — filtering/sorting happens in Python via `_permit_type_status` / `_filter_dashboard_items` / `_sort_dashboard_items` helpers, and `Employee.next_expiration` / `Equipment.next_expiration` properties in `models.py` (nearest upcoming non-N/A expiration; Employee's includes the license). Filter semantics: `permit_type` alone = that type needs attention (expired/expiring/missing — an absent permit row counts as missing); `permit_type` + `permit_status` = that type has exactly that status; `permit_status` alone = any permit has it. `exp_month` (via `_expires_in_month`) matches entities with any non-N/A permit — or the driver's license on Empleados — expiring in that month (past dates included; deliberately NOT built on `next_expiration`, which drops past dates); with `permit_type` set, only that type's expiration (or `license_expiration` for `LICENCIA`) counts, and the month **replaces** the type's needs-attention rule — otherwise a far-future month + type would always be empty since 'valid' is excluded by `ATTENTION_STATUSES`. Tile counts (`tile_counts` from the route) are computed **after** the scope filters (`permit_type` / `exp_month`) but **before** the `permit_status` filter, so they stay stable while a tile is active (the queue `severity_counts` invariant). Invalid param values silently reset to defaults. Empty panels under active search/type/status filters say "No hay resultados con estos filtros". Equipment `.entity-meta` lines show `plate · model` (all three panels) so the `category` sort is legible; employee cards already showed `area`. **Page layout (Inventory-style):** `.stat-tiles` → one flat **`.toolbar`** row holding TWO separate forms side by side: the search `<form class="search-wrap">` (icon absolutely positioned inside the input; carries hidden inputs for ALL other params) and the auto-submit `<form class="filter-form">` (selects; carries hidden `view`/`search`/`status`/`permit_status`). `.toolbar .filter-form { display: contents }` dissolves the second form into the toolbar's flex row so all controls sit inline; `.spacer` pushes the manager-only "Nuevo Empleado/Equipo" button to the right edge. The two forms MUST stay separate (each cross-preserves the other's params via hidden inputs) — when adding a param, add its hidden input to BOTH forms. The dashboard is the **one list page with no `.page-titlebar` kicker header** (removed 2026-09-01): its title said nothing the sidebar's active nav link and the tiles' own "Empleados"/"Equipos" total label didn't already say, and it cost a band of above-the-fold height on phones. The tiles are the first element inside `.dashboard` — do not re-add a titlebar here. The shared `.page-titlebar` CSS stays because every other list/tool page still uses it.

**Sticky list preferences (`list_prefs.py`)**: the dashboard and the issue queue both drive off GET params, but nothing carried those params off the page — the sidebar links are bare (`base.html`), and ~20 post-edit redirects drop the query string — so a user who works one slice ("Equipos, clase camión, por vencer") lost it on every navigation. Each user's **normalized** choices are therefore stashed in the Flask session under `list_prefs`, keyed per list (`dashboard:employees`, `dashboard:equipment`, `issues:queue` — the dashboard key is **per view** because `permit_type`/`equipment_class`/`exp_month` are view-scoped). The `nav_args` dict each context helper already returns IS the set worth storing, so `remember_list_args()` is a filter over it (values coerced to `str`, since `equipment_id` is read back with `type=int`) and `restore_list_args()` merges it back into `request.args`. **The restore lives at the top of `_dashboard_context` / `_queue_context`, not in the routes**, so `_sibling_nav` / `_issue_sibling_nav` inherit it — a detail page reached from a param-less redirect rebuilds the remembered list, which is what fixes the prev/next arrows and back-link on all those redirect paths without editing them. **Restoring only happens when the request names no list state at all**: `if 'search' in args or any(p in args for p in params): return args` — the moment a request names a param, *including naming it empty* (which is exactly what the auto-submit filter form does when a select returns to "Todas"), the user is steering and args win whole. `view` is deliberately not a pref param, so the sidebar's `?view=equipment` still restores that view's filters. **`search` is deliberately NOT remembered** on either list (a sticky search term reads as missing records); the pref sets are `DASHBOARD_PREF_PARAMS` and `QUEUE_PREF_PARAMS` — **a new list param belongs in its tuple** or it silently stops surviving navigation. Saving happens in `dashboard()` / `queue()` only, and an empty result pops the key, so browsing a list back to its defaults forgets it. Escape hatch: both pages have a **"Limpiar filtros"** link pointing at `?reset=1`, which calls `forget_list_args()` and redirects to the clean URL (a bare URL alone would just restore). On the dashboard the link is gated on the new `filters_active` (which **includes** `sort_by != 'name'`, since sort is sticky and must be resettable); on the queue it is gated on `prefs_active` (`filters_active or sort_by != 'unit'`) — **`sort` must stay out of the queue's own `filters_active`**, which also hides empty trucks and switches the panels to the "no results" text. Preferences last 30 days (`PERMANENT_SESSION_LIFETIME` in `config.py`, `session.permanent = True`) and survive logout on that device; the bucket carries a `list_prefs_uid` owner stamp and is dropped wholesale when another user logs in on the same browser.

**Company-level permits**: `CompanyPermit` model tracks permits scoped to companies (LB/PLI) rather than individual employees or equipment. `COMPANY_PERMIT_TYPES` defines eight types: the four per-class insurance policies (`SEGURO_TRUCK/CHASSIS/TANK/GENERATOR` — "Seguro — Camiones/Chasis/Tanques/Generadores"), Certificado HazMat, Certificado NMFTA (PLI-only), USDOT Biennial Report, Franquicia NTSP — each with a list of applicable companies. Same status property pattern (expired/expiring_soon/valid/missing/na) as employee and equipment permits. Unique constraint enforces one permit per type per company. Edited via the "Empresa" dashboard view (`company_permit_edit` / `company_permit_upload_form` routes; the view auto-backfills missing rows on visit).

**Shared per-class insurance (SEGURO_*), selectable per vehicle**: LB/PLI equipment normally shares one insurance policy **per equipment class** (trucks, chassis, tanks, generators — one `CompanyPermit` of each per company), but each vehicle can now **override which policy covers it** or opt out entirely. `Equipment.insurance_policy_type` (`String(30)`, nullable) is the three-state control: **NULL = automática** (follow `equipment_class`, the historical behavior — hence no backfill was needed), a **`SEGURO_*` code** = that shared policy regardless of class, and **`INSURANCE_OWN` (`'OWN'`)** = the vehicle is not covered by a company policy and carries its own editable per-vehicle SEGURO permit — surfaced in the UI as **"Compulsorio"** (see the Compulsorio bullet below). It stores the *permit-type code, not a `company_permit_id` FK*: `CompanyPermit` identity already is `(company, permit_type)`, the boot-time schema sync only does `ADD COLUMN` (it would never enforce an FK), and the Empresa view auto-backfills deleted policy rows — which would orphan an id but not a code. **`Equipment.insurance_permit_type` (models.py) is the single resolution point** — it returns the covering `SEGURO_*` code, or **`None`** when the vehicle is on its own policy (explicit `OWN`, or `company == 'Personal'`) — and `equipment_detail`, the Excel export and the PDF all read it instead of re-deriving the class inline. `Equipment.insurance_card_title` pairs with it; **`INSURANCE_CARD_TITLES` is keyed by permit-type code, NOT by class** (it was rekeyed when the override landed). `models.sync_vehicle_insurance_permit(equip)` keeps the per-vehicle SEGURO `EquipmentPermit` aligned — `'N/A'` when a shared policy covers the vehicle, `'YES'` when it does not, creating the row if absent — and it **deliberately does not clear `expiration_date`** (unlike the `/toggle` routes) so flipping to a shared policy and back restores the vehicle's own dates. It lives in `models.py` precisely so `app.py` and `issues/routes.py` can both call it; `equipment_new`, `equipment_edit` and **both branches of the equipment Excel import** do (the import call is what finally fixes a sheet reassigning a vehicle's company/class leaving a stale active SEGURO — `equipment_edit` never touched permits before). Note the import's `permit_info` only ever carries `MARBETE`/`INSPECCION`/`NTSP`: the sheet's **"Seguro" column is the free-text carrier name** (`insurance_company` in `EQUIPMENT_COLUMN_ALIASES`), never a permit date — so there is no SEGURO cell to skip on a policy-covered vehicle, and guarding the permit loop against one is dead code. The sync call alone is what that path needs. The form control is a **"Póliza de Seguro" select** in `equipment_form.html` (options from `INSURANCE_POLICY_CHOICES`, derived from `COMPANY_PERMIT_TYPES` so labels live in one place), validated by `_resolve_insurance_policy(form, company)` in `app.py` — the `_resolve_equipment_class` idiom: unknown values silently reset to automática, and **Personal always resolves to `OWN`** (an inline script in the template mirrors that client-side, but the server is authoritative). The per-vehicle `EQUIPMENT_PERMIT_TYPES` list still uses plain `'SEGURO'` — do NOT rename that one. `vehicle_create` (issues) still inlines its own N/A rule, which stays correct because it only creates LB/PLI trucks at NULL/automática. The PDF and Excel Seguro columns both resolve through `_insurance_permits_by_equipment` — see the PDF report bullet. `flask dedup`'s equipment merge field list includes `insurance_policy_type` so an override survives a merge. The idempotent `flask migrate-class-insurance` command renamed the old single SEGURO row to SEGURO_TRUCK in place (preserving id/file/dates; merge branch handles a pre-created blank) and created the other three slots — run once per environment after deploy. Alert counts are not double-counted (per-vehicle SEGURO is N/A whenever a policy covers the vehicle; each class policy counts once on the Empresa view).

**Compulsorio (the label for `INSURANCE_OWN`, corrected 2026-09-02)**: the compulsorio is **not its own permit row, permit type, or policy category** — it is simply what a unit that is **not covered by a company policy** carries, so it is the UI label for the existing `INSURANCE_OWN` state, not a state beside it. Its expiration date, number and document live on that vehicle's **own `SEGURO` `EquipmentPermit`** (the one `sync_vehicle_insurance_permit` keeps at `'YES'`), which is why the equipment page renders an ordinary **"Seguro / Insurance"** card — with a `.permit-shared-note` line reading "Compulsorio — no cubierto por una póliza de empresa." — rather than a retitled one. The form select therefore offers exactly one non-company option (`value="OWN"`, labeled "Compulsorio"); Personal equipment resolves to it automatically since it has no company policies. It is never auto-applied to LB/PLI equipment: `INSURANCE_TYPE_BY_CLASS` (both the class map and the automática fallback) contains only `SEGURO_*` codes, so only an explicit selection can leave a vehicle off a company policy. **`LEGACY_INSURANCE_POLICY_TYPES = {'COMPULSORIO': INSURANCE_OWN}`** exists because a first pass (commit `a138557`) shipped Compulsorio as its own `'COMPULSORIO'` code for a day: `Equipment.insurance_permit_type` and `_resolve_insurance_policy` both normalize through it on read, so a row saved in that window can never fall through to the class fallback and read as *company-covered*, and a boot statement beside the CPR rename rewrites the surviving rows (idempotent, mirrors `LEGACY_ISSUE_STATUSES`). No column, constraint, CLI command or report change was needed at any point.

**Archive feature (soft-remove for departed employees / sold-scrapped equipment)**: Both `Employee` and `Equipment` carry three nullable columns — `archived_at` (DateTime), `archive_reason` (String(30) code), `archive_note` (String(300)) — added via the boot-time additive schema sync (Postgres `ADD COLUMN IF NOT EXISTS`; existing local SQLite DBs need a recreate or manual ALTER). **`archived_at IS NULL` is the single visibility invariant** — all new filtering keys on it, never on `status`. Reason codes live in `models.py`: `EMPLOYEE_ARCHIVE_REASONS` (baja/renuncia/otro) and `EQUIPMENT_ARCHIVE_REASONS` (vendido/chatarra/otro), with `is_archived` / `archive_reason_label` properties on both models. Archiving ALSO sets `status='inactivo'` (restore → `'activo'`) so the pre-existing status-aware surfaces stay correct; to prevent divergence, `employee_edit`/`equipment_edit` skip the status assignment for archived records and the form select renders `disabled`. Routes: `/employee/<id>/archive|restore` and `/equipment/<id>/archive|restore` (POST, `@manager_required` — hard delete stays admin-only), plus `/archive` (`archive_view`, sidebar "Archivo" link, `templates/archive.html` — two panels newest-first with reason label + `mm/dd/yyyy` date, searchable; restore lives on the detail page only). The detail pages show a `.archived-banner` + "Archivado" status tag + Restaurar button; the Archivar button opens an inline collapsible `#archive-panel` (reason select + optional note, `toggleArchivePanel()`). Surfaces that exclude archived: dashboard queries + tile counts, `generate_pdf` (employees, equipment, AND the open-issues join — dead work items), `_gather_expiring_items` (notifications), `reportable_equipment_query` (driver dropdown, queue panels, manual create), the queue's main/status/severity/resolved queries (outerjoin + `Issue.equipment_id IS NULL OR Equipment.archived_at IS NULL` — unlinked issues stay visible), and the driver report link (archived employee ⇒ `issues/link_inactive.html` with HTTP 410; `access_token` is NOT cleared, so restore reactivates the link). `employee_detail`'s write-on-read permit backfill is skipped for archived records. Excel imports skip rows matching an archived record and report `N omitidos por archivado`. `find_duplicate_equipment` deliberately still matches archived rows (the Postgres partial unique indexes are archive-blind; the duplicate flash gains an "equipo archivado" hint) — reusing a sold truck's unit#/VIN requires hard-deleting the archived row. `flask dedup` merge field lists include the three archive columns so archive metadata survives into the keeper. Issue detail pages for issues on archived equipment stay reachable (history preserved). CSS: `.status-archivado`, `.archived-banner`, `.archive-panel`, `.entity-card--archived` (missing-color tokens, theme-aware).

**Mobile optimization**: CSS has three responsive breakpoints (1024px, 768px, 480px). At 768px: sidebar becomes off-canvas drawer, main content gets full viewport width, grids collapse to 1 column, touch targets enforce 44px minimum (the list includes the queue's `.issue-row` at 48px), and the queue's `.issue-status-tabs` strip gets a right-edge `mask-image` fade as a scroll hint (alpha-only mask — theme-proof, no color token). At 480px: modals go full-screen, report form submit button is sticky, tighter spacing, `.stat-tiles` switches to the compact treatment (see the stat-tiles notes), and the detail pages' prev/next buttons drop `.detail-nav-name` to become arrows-only (the sibling's name doesn't fit beside the back-link). The coarse-pointer block gives `.detail-nav-btn`/`.detail-nav-count` a 44px min-height. Touch feedback via `@media (hover: none) and (pointer: coarse)` targets touch devices with `:active` states without affecting desktop hover. The queue's collapsible headers (truck cards + Cerrados) are keyboard-accessible: `role="button" tabindex="0" aria-expanded aria-controls` in the markup, a shared `setCollapsed()` helper syncing chevron + `aria-expanded`, and an Enter/Space keydown handler — all in `queue.html`'s inline script; `:focus-visible` ring via `--focus-ring`.

**iOS input-zoom prevention (literal 16px, not rem):** the root is `html { font-size: 15px }` (14px at 480px), so `1rem` on an input computes *below* iOS Safari's 16px zoom threshold. The fix is a **literal `16px`** — set in the 768px `.form-group input/select/textarea` block (whose selector list also covers `.filter-form select`, `.toolbar select`, `.search-wrap input`, `.input-icon input`) AND, as a catch-all for every text control regardless of breakpoint, in the touch-device rule `@media (hover: none) and (pointer: coarse) { input, select, textarea { font-size: 16px } }`. Do NOT change these back to `rem` — that reintroduces the zoom bug. That same touch media query also bumps `.btn-sm` to 40px min-height and gives `.truck-edit-link` (the admin "Ver ficha" link nested inside a tappable queue card header) real vertical hit area.

**Safe-area / notch handling (`env(safe-area-inset-*)`):** the viewport meta in `base.html` is `viewport-fit=cover` so `env()` insets resolve to real values on notched iPhones in standalone PWA mode (the status bar is `black-translucent`, which overlays content). Insets are applied to `.mobile-topbar` (top + horizontal), the mobile `.main-content` top padding (both 768px and 480px rules — `calc(56px + env(safe-area-inset-top) + …)`), the sticky `.report-form .form-actions` (bottom), the full-screen `.modal` (top+bottom), and the drawer `.sidebar` (top+bottom). All are `env()`/`max()` based, so they are no-ops on non-notched devices and desktop. `body` also has `overscroll-behavior-y: contain` to stop the iOS rubber-band from revealing the fixed shell.

The one real data table (`admin_users.html`) is the exception to the app's otherwise card-based layouts: `.users-table-container` uses `overflow-x: auto` + `.data-table { min-width: 640px }` so it scrolls horizontally on phones instead of cramming, and the inline edit form lives in its own full-width `colspan="6"` row (`td.inline-edit-cell`, zero padding/border so it collapses when the form is hidden) rather than trapped in the narrow "Acciones" cell.

## Key Patterns

- Templates use Jinja2 with a shared `base.html` layout (sidebar + navbar). Use `versioned_static('path')` instead of `url_for('static', filename='path')` for CSS/JS to enable cache busting.
- Dark/light theme uses `data-theme` attribute on `<html>`, persisted in `localStorage`. An inline `<script>` in `<head>` sets the theme before first paint to prevent FOUC; `app.js` handles toggle buttons, syncing, and updating `<meta name="theme-color">` dynamically. The sun/moon toggle (`.theme-toggle` + `.theme-btn`) lives in **two** places: the desktop **sidebar footer** (`.theme-toggle-sidebar`, above the user-info/logout) and the **mobile top bar** (`.theme-toggle-mobile`, hidden on desktop). `syncThemeButtons()` queries *all* `.theme-btn` nodes, so both groups stay in sync automatically — adding a third group anywhere Just Works. (There is no floating/fixed toggle; an earlier `.theme-toggle-floating` was removed because its `position:fixed; top/right; z-index:1000` overlapped each page's top-right action buttons.)
- Branding: the top-left brand area shows the **two company logos side by side** (`logo-lb.png` + `logo-pli.png`), not a text title — in the desktop sidebar header (`.sidebar-header .logo`, images use the `.logo-img` class; `.logo` is `flex:1` + `justify-content:center` so the pair sits centered with the `.sidebar-toggle` pinned right) and in the mobile top bar (`.mobile-topbar-logos` / `.mobile-topbar-logo`). The old `.mobile-topbar-title` text rule is now unused. Same logos also appear on the login card (`.login-company-logo`) and dashboard/queue company headers (`.company-logo`).
- Mobile navigation: On screens <= 768px, the sidebar becomes a hidden off-canvas drawer (280px, slides from left). A fixed 56px mobile top bar with hamburger menu, company logos, and theme toggle replaces the desktop sidebar. `openDrawer()`/`closeDrawer()` in `app.js` manage state. Swipe gestures (edge-swipe to open, swipe-left to close) are supported via passive touch listeners. `toggleSidebar()` delegates to drawer functions on mobile; on desktop it toggles **`html.sidebar-collapsed`** (CSS-driven 64px icon rail — logos/labels/user-info hidden, active nav-link switches to a bottom accent border, theme toggle stacks vertically) and persists it in `localStorage['sidebar-collapsed']`. The `base.html` inline head script re-applies the class **pre-paint** (same IIFE as the theme), so there's no flash on load; a 768px override block makes the drawer win over a stored desktop collapse (full 280px width, labels restored).
- PWA: `static/manifest.json` (served also at `/manifest.json`, `scope: "/"`), `static/sw.js` (service worker with cache-first for static assets, network-first for HTML), and app icons in `static/img/icon-*.png`. PWA meta tags in `base.html` are wrapped in `{% block pwa_meta %}` and service worker registration in `{% block service_worker %}` so child templates can opt out. Driver report pages (`report.html`, `report_success.html`) override both blocks to strip PWA signals — "Add to Home Screen" creates a plain browser bookmark, not a standalone app install. Report pages also unregister any previously-cached service worker on the driver's device.
- File uploads go to `uploads/` directory with UUID-prefixed filenames
- **Permit-card attached file has one view link, not two:** each permit card shows the attached PDF via a single `.file-link` "Ver documento" in the **card body** (visible to all roles). The manager-only `.permit-card-footer` keeps only Editar / Eliminar (delete the attached form) / Subir-Reemplazar — it does NOT re-link the file (an earlier redundant "Ver formulario" footer link was removed). Applies to `employee.html`, `equipment.html`, and both LB/PLI panels in `dashboard.html`. Do not re-add a footer view link.
- **Destructive delete buttons show icon + "Eliminar" text** (not icon-only): the entity-delete buttons on `employee.html`, `equipment.html`, and the per-row delete on `admin_users.html` all render `<i class="fas fa-trash"></i> Eliminar`, matching the permit-form delete buttons. Keep new delete controls labeled, not icon-only.
- Excel import (openpyxl) includes a 2-digit year fix (1930→2030) for date handling. Both employee and equipment imports recognize N/A-like cell values ("N/A", "NA", "NO", empty string) and set `applicability='N/A'` on the corresponding permit.
- **Equipment import is header-driven, never positional (`import_equipment`):** every column is located by its **header text** via `EQUIPMENT_COLUMN_ALIASES` (`app.py`, above `find_duplicate_equipment`) — a list of `(field, aliases)` pairs matched against `_normalize_header()` output (accent-stripped, upper-cased, punctuation→space) by `_map_equipment_columns()`: **exact match first, then substring**, each column claimed once, so a generic alias (`SEGURO`) can't steal a more specific column. Fields: `titular / unit / company / clase / make / model / year / vin / plate / insurance / MARBETE / INSPECCION / NTSP / cost`. This replaced a hardcoded `row[0..12]` mapping that silently shifted every field when the master spreadsheet gained a column (models landing in `vin_serial`, years in `plate_number`, MARBETE/INSPECCION dates blanked wholesale, and rows whose Compañía cell moved out from under the reader defaulting into LB). Three guards flow from it: (1) `_missing_equipment_columns()` **aborts the whole import** with a Spanish message naming the unresolvable columns plus the headers it did find, unless the sheet has a Compañía column and at least one identity column (Unidad/VIN/Tablilla); (2) `_resolve_company(company_cell, titular_cell)` returns `None` for a blank/unrecognized company instead of **defaulting to LB** — those rows are counted in `sin_empresa` and reported in a warning flash, never misfiled (the old `else: company = 'LB'` is what put PLI/Personal vehicles in the LB panel); (3) a permit column that is **absent from the sheet** is skipped entirely rather than parsed as empty, so a trimmed-down spreadsheet can't blank stored expiration dates. The update path now also corrects `existing.company` when the sheet disagrees (counted as `reasignados` in the flash) — without it a bad import could never be undone by re-importing — and fills `make` (new sheets split Marca/Modelo). `_resolve_import_class()` reads the Clase/Tipo column against `EQUIPMENT_CLASSES` labels/codes and falls back to `classify_equipment(model)` for older sheets that put the class word in Modelo.
- **Unified Excel-import page (`templates/import.html`, route `import_data`, admin-only):** one tabbed page is the single entry point (sidebar "Herramientas" → "Importar Excel") for **all three** Excel imports — **Empleados** (posts to `import_data`), **Equipos** (posts to `import_equipment`), and **Reportes** (the issue-report backlog import, posts to `issues.import_issues`). The Empleados/Equipos tabs share one `import_token`; the Reportes tab uses a **separate** `issue_import_token` (both minted in the `import_data` GET, which also passes `ISSUE_CATEGORIES/SEVERITIES/STATUSES` for the Reportes tab's info block). `switchTab()` toggles all `.import-container`s generically and each tab wires its own `setupUpload(...)`. The Reportes form still posts to the unchanged `issues.import_issues` handler, which renders `issues/import.html` as the result view. The old standalone entry points were removed: no "Importar Lote" button on the queue and no "Importar Reportes" link in the Taller sidebar. `issues.import_form` (GET) remains defined but unlinked.
- **PDF report (`generate_pdf` route → `report_pdf.html`):** a single color-coded report covering **three categories, each split by company** — Empleados (LB/PLI), Equipos (LB/PLI/Personal), and **Averías/Issues** (LB/PLI). The `?type=` arg (`all`|`employees`|`equipment`|`issues`|`company`) and `?company=` arg scope the report (chosen via the `report_menu` picker at `/reports` → `report_options.html`, which now offers **two** submit buttons — "Descargar PDF" and "Descargar Excel" via `formaction`); the sidebar link is labeled "Reportes" and goes to that menu; the menu's own default plus any direct link with no args yields the full `type=all`. **The querysets are shared**: `_gather_report_data(report_type, company_filter)` returns `(employees, equipment_list, issues, company_permits)` and both `generate_pdf` and `export_excel` consume it (archived excluded, open issues only — scoping can't drift between formats). **The Seguro column is likewise shared**: `_insurance_permits_by_equipment(equipment_list)` (`app.py`, right below `_gather_report_data`) resolves each vehicle to the `CompanyPermit` covering it or its own `EquipmentPermit` via `Equipment.insurance_permit_type`, and the PDF receives it as an `insurance_by_eq` map keyed by equipment id (the template's three equipment tables special-case `SEGURO` inside their `['MARBETE', 'SEGURO', 'INSPECCION']` loop). Before that the PDF read the per-vehicle SEGURO unconditionally and so rendered `—` for **every** LB/PLI row while Excel showed the real shared policy — when touching either format, change the helper, not one call site. **The report title is type-aware:** a Jinja `report_titles` map at the top of `report_pdf.html` turns `report_type` into both the `<title>` and the `<h1>` — `all`→"Reporte General", `employees`→"Reporte de Permisos", `equipment`→"Reporte de Equipos", `issues`→"Reporte de Averías", `company`→"Reporte de Permisos de Empresa" (`.get(..., 'Reporte General')` fallback). The per-section company banners (e.g. `LB Caribe Services — Empleados`) are separate sub-headings and stay as-is. **Permit** cells are color-coded by expiration status (the `status_cell` macro: valid/expiring/expired/missing/na, 30-day window via `today`/`alert_date`). **Issues** are **open only** (`current_status.notin_(RESOLVED_STATUSES)`), joined to `Equipment` for their company, sorted company → vehicle (unit #/`display_name`) → newest, and color-coded by severity (`.sev-{baja,media,alta,critica}`, hardcoded hex mirroring the `--color-sev-*` tokens since the template is self-contained inline CSS). Rendered via WeasyPrint to a downloadable PDF; **the route catches broad `Exception` (not just `ImportError`) and falls back to returning the printable HTML** — WeasyPrint's native libs (Pango/Cairo/gobject) are absent in local macOS dev where the import raises `OSError`, so the fallback keeps the route from 500-ing (real PDFs are produced in the Dockerized Railway env). Issue labels come from `Issue.category_label`/`severity_label`/`status_label`; reporter name via `Issue.reporter.name`.
- **Excel export (`export_excel` route, `GET /export/excel`):** openpyxl workbook mirroring the PDF's scoping via `_gather_report_data`, same `?type=`/`?company=` args. Up to four sheets — **Empleados** (one column per `EMPLOYEE_PERMIT_TYPES` + Licencia), **Equipos** (Clase column from `equipment_class_label`; the Seguro cell comes from the shared `_insurance_permits_by_equipment` map — the vehicle's company policy, or its own SEGURO permit for own-policy/Personal vehicles — see the PDF bullet), **Averías** (open only, severity-tinted), **Empresa**. Empty sheets are skipped. Date cells are real `date` objects with `number_format='MM/DD/YYYY'`; status fills use `_XLSX_STATUS_COLORS`/`_XLSX_SEVERITY_COLORS` (module constants above the route, hex-mirroring the light-theme status tokens). Download name `reporte_{type}_{company|todas}_{YYYYMMDD}.xlsx`.
- **License document upload (employee detail):** the "Licencia de Conducir" card has a manager-only `.permit-card-footer` mirroring the permit-card widget — Eliminar + Subir/Reemplazar via hidden auto-submit form posting to `employee_license_upload_form`/`employee_license_delete_form` (`/employee/<id>/license/upload-form|delete-form`, `@manager_required`). Upload accepts the full `allowed_file()` set (licenses are often images), not PDF-only. All file-replace paths (`employee_edit` license, `employee_permit_edit`, `equipment_permit_edit`, the upload-form routes) call `delete_stored_file()` on the old blob before overwriting — do not reintroduce the orphaning pattern.
- **Uploaded documents are manual-only — Excel imports can never touch them (`protect_uploaded_files()` in `models.py`):** the three Excel importers (`import_data`, `import_equipment`, `issues.import_issues`) are decorated with `@protect_uploaded_files()`, a re-entrant `contextmanager` (usable as a decorator, thread-local flag) that arms a `before_flush` listener on `db.session`. While armed: (1) any change to a document column on a **dirty** row is reverted to its committed value (the row's other changes — `expiration_date`, `applicability`, `model`, … — still commit normally) and logged as a warning; (2) a document column set on a **new** row is cleared; (3) deleting a `FileStorage` blob, or deleting any row that still has a document attached, raises `ProtectedFileError`, which each importer catches ahead of its broad `except` and turns into a Spanish "Importación cancelada para proteger documentos adjuntos" flash — the whole import rolls back rather than losing a file. The guarded columns live in the `PROTECTED_FILE_FIELDS` dict (keyed by **class name**, not class object, so it sits above the models without import-order games): `Employee.license_file`, `file_path` on `EmployeePermit`/`EquipmentPermit`/`CompanyPermit`, `IssuePhoto.storage_filename` — **add new document columns there**. The guard is inert outside the context manager, so every manual route (`employee_edit`, `*_permit_edit`, the `upload-form`/`delete-form` routes) replaces and deletes files exactly as before. `flask dedup` and `flask migrate-class-insurance` are deliberately **not** guarded — they legitimately move `file_path` onto a keeper row and delete the loser.
- **Record-to-record navigation (prev/next on detail pages):** every detail page — `employee.html`, `equipment.html`, `issues/detail.html` — renders a `.detail-nav` widget (← previous · `N de M` · next →) via the shared `{% include '_detail_nav.html' %}` partial, sitting in a `.detail-topbar` flex row beside the back-link. The arrows walk **the same filtered + sorted sequence the list rendered**, not raw id order. Mechanism: the list params ride into every entity link as query args — the `nav_args` dict each context helper returns is the **single source** of which params those are — so `dashboard.html`'s cards use `url_for('employee_detail', id=emp.id, **nav_args)` and `queue.html`'s `issue_row` uses `url_for('issues.detail', issue_id=issue.id, **nav_args)`. The detail route then **rebuilds the list** from those args through the very helper the list page uses — `_sibling_nav(view, id, request.args)` → `_dashboard_context(..., with_counts=False)` (flattened LB → PLI → Personal; the tile totals are skipped since their per-item `permit_status_summary` loads every permit row) and `_issue_sibling_nav(id, request.args)` → `_queue_context(..., with_counts=False)` (flattened LB truck cards → PLI truck cards → "sin unidad" → Cerrados) — so the arrows can never drift from what was on screen. `nav_args` holds only **non-default normalized** values (the `... or none` idiom), so a default-view URL stays clean and a junk param can't propagate. Each helper returns `{prev, next, position, total, list_url}` or **`None`** when the record isn't in that list (archived, or filtered out) — the partial then renders nothing, and the back-link falls back to its plain `url_for`. Otherwise the back-link and the `N de M` counter both point at `nav.list_url`, so returning to the list preserves the filters. Keyboard ← / → are bound by `initDetailNavKeys()` in `app.js`. **When adding a new list param, add it to the `nav_args` dict in the context helper** (alongside its hidden inputs in BOTH toolbar forms, and its entry in the matching `*_PREF_PARAMS` tuple — see Sticky list preferences) — otherwise the arrows silently walk an unfiltered list.
- **Date display format is `mm/dd/yyyy`** everywhere user-facing (US order): all Jinja `strftime` output in templates (`employee.html`, `equipment.html`, `dashboard.html`, `admin_users.html`, `issues/detail.html` with `%H:%M`, `report_pdf.html`, `email/permit_expiry_notice.html`), and the `time_ago` fallback in `app.py`. Exceptions that stay as-is: `<input type="date">` `value=` fields use ISO `%Y-%m-%d` (browser-native, required); the Excel-import date **parsers** (`app.py` `to_date`, `issues/routes.py`) accept a tuple of formats incl. both `%d/%m/%Y` and `%m/%d/%Y`; the PDF filename stamp uses `%Y%m%d`; and the PDF "Generado" line uses the long-form `%d de %B de %Y`. There is no shared date filter — each display site hardcodes the format, so keep new dates on `%m/%d/%Y`.
- Auth uses Flask-Login with strict module separation enforced by a `before_request` hook. Base roles: admin, manager, viewer. Issue module uses `user_issue_roles` table (shop role only; office role is deprecated). Any non-admin user with a shop issue role (viewer + shop OR manager + shop) can ONLY access the issue module — they are redirected away from all permit routes. Permit users (viewer/manager without shop role) can ONLY access the permit module. Admin has full access to both modules. `User.is_shop_only` and `User.has_shop_role` model properties centralize this logic. `User.is_shop_manager` (`is_manager and has_shop_role` — i.e. admin, or base-role `manager` + shop role) gates the extra ability to manually create reports, distinguishing a shop manager from a shop viewer (the only place base role + shop role are combined).
- Drivers access issue reporting via link-based auth: each employee has an optional `access_token` (UUID) column; URL `/issues/report/<token>` identifies the driver without login. Report pages extend `base.html` but override `{% block pwa_meta %}` and `{% block service_worker %}` to disable PWA installation — drivers who save the link to their homescreen get a browser bookmark, not the full app. The report form has **one shared truck selector** at the top and a **repeatable set of problem rows** — each row collects category, severity, and description only (odometer/location columns exist in the DB but are not exposed in the UI). A driver can submit **multiple problems in one request**, each becoming its own independent `Issue` on the same truck. Truck dropdown is scoped to `equipment_class == 'truck'` vehicles from the driver's company (Personal excluded; `EXCLUDED_EQUIPMENT_MODELS` survives only as a NULL-class fallback). The `reportable_equipment_query()` helper in `issues/routes.py` centralizes this filtering, and `reportable_equipment_list()` is what the form actually renders (natural unit-number order).
- **Multi-issue driver submission:** the driver form posts the problem fields as **parallel arrays** — `category[]`, `severity[]`, `description[]` — read in `report_submit` via `request.form.getlist(...)` (order-preserving, so the three stay index-aligned with no per-row index bookkeeping). `report()` passes `problem_rows=[{}]` (one blank row) so the template has a uniform variable to iterate; on a validation error `report_submit` re-renders with the submitted `problem_rows` so entries persist. Rows that are **fully empty** (blank category AND description) are dropped so a stray added row can't block the batch; **at least one** non-empty row is required. Validation is **all-or-nothing** — any invalid row flashes a Spanish error naming the offending "Problema N" and re-renders with HTTP 422, saving nothing. On success it **loops the single-issue create pattern** (`Issue(...)` → `db.session.add` → `db.session.flush()` → `update_issue_status(issue, 'reportado', changed_by_employee_id=…, notes='Reporte inicial del chofer')`) once per row, collecting ids, then does **one** `db.session.commit()` (same batch idiom as `import_issues`). It redirects with `issue_ids=1,2,3`; `report_success` parses that CSV into a list and `report_success.html` shows one-vs-many wording. The repeatable rows are pure template + a self-contained `<script>` in `report.html` (a hidden `<template id="problem-row-template">` cloned on "Agregar otro problema", renumbering the visible "Problema N" headings and hiding the `.problem-row-remove` `×` when only one row remains) — there is no repeatable-row helper in `app.js`. Per-row HTML `required` is intentionally omitted (server enforces) so a removed/blank row can't trip native validation; the truck `<select>` keeps `required`. `.problem-row*` CSS lives in the driver-report block in `style.css` (remove button is a 44px touch target on coarse pointers).
- Issue status updates are transactional: `Issue.current_status` (denormalized) and `IssueStatusHistory` are always updated in the same commit. `resolved_at` auto-sets on transition into `RESOLVED_STATUSES` (i.e. `cerrado`) and is cleared when an issue is reopened.
- **No future-dated issue reports:** `_is_future_date()` (`issues/routes.py`) guards every path that sets an issue's `reported_at`/`resolved_at` so a date after today (server date) is rejected — the manual-entry route `create()` adds a Spanish error and re-renders with HTTP 422; the bulk import counts the row as errored and `continue`s (nothing persists). This exists because `_coerce_date`'s 2-digit-year `+100` bump (correct for e.g. `25`→2025) could turn a spreadsheet `1935`/`35` into `2035`; the guard catches the pathological result at point-of-use rather than removing the bump other importers rely on. The **driver report flow never sets a date** (`report.html` has no date field on any problem row; `report_submit` relies on the `Issue.reported_at` default `datetime.utcnow` for every issue it creates) — do NOT add a date field there.
- Unique constraints enforce one permit per type per employee/equipment
- `dedup` CLI command uses advisory locking and idempotency tokens for safe bulk operations. It merges duplicate employees (by name+company), employee permits, equipment permits, and **duplicate equipment/vehicle rows**. Equipment vehicles are deduped by **union-find over shared signatures** — two rows are the same vehicle if they share ANY non-blank key: `vin_serial` (global), `plate_number` (global), or `unit_number`+`company` (per-company), all normalized lowercase/trimmed. (Union-find, not a single cascade key, so a VIN-only row and a plate-only row for the same truck still merge.) Keyless rows (no VIN/plate/unit — e.g. carretones, generadores, tanques) fall back to a `(company, titular, model, year)` signature so exact-duplicate copies still merge; a keyless row with titular AND model both blank is never auto-merged. It keeps the lowest-id row, fills its empty fields from dups, merges/re-points child `EquipmentPermit` rows, and reassigns linked `Issue` reports to the keeper before deleting (the `Issue.equipment_id` FK is `SET NULL`, so issues would otherwise be orphaned). It also removes **duplicate issue reports** left by repeated bulk imports, grouping by `(equipment_id, category, normalized description, canonical report day)` (keeps lowest id; re-points any `parent_issue_id` to the keeper; child `IssueStatusHistory` rows cascade-delete). The "canonical report day" comes from `_canonical_report_day()` in `issues/routes.py` (reused here via a local import so the cleanup and importer can never drift): it returns `reported_at.date()` ONLY when the timestamp is exactly midnight — real spreadsheet dates are stored at midnight via `_as_datetime`, whereas a missing date fell back to `datetime.utcnow()` (a non-midnight wall-clock time), so dateless rows resolve to `None` and collapse together regardless of which day each import stamped them. This is what lets `flask dedup` finally merge the dateless duplicates that the old `reported_at.date()` key kept splitting across different days.
- **Duplicate-vehicle defenses (3 layers, all reuse `find_duplicate_equipment(vin, plate, unit, company, titular=, model=, year=)` in `app.py` — a case-insensitive VIN→plate→unit#+company cascade lookup, with a keyless fallback to `(company, titular, model, year)` when VIN/plate/unit are all blank so keyless vehicles aren't duplicated on re-import):** (1) `equipment_new` and `vehicle_create` (`issues/routes.py`) block the save on a match — Spanish warning, re-render with submitted values, HTTP 422; `equipment_form.html` repopulates via `form_data`. (2) The Excel equipment import (`/import/equipment`, app.py) uses the **same helper** for its upsert lookup, so re-importing the master spreadsheet updates vehicles in place (matching by unit# even when VIN/plate are blank) instead of creating duplicates — this was the recurring duplicate source. (3) `dedup` applies **partial unique indexes** (Postgres) as a permanent backstop: `uq_equipment_vin` on `lower(vin_serial)`, `uq_equipment_plate` on `lower(plate_number)`, `uq_equipment_company_unit` on `(company, lower(unit_number))`, each `WHERE <col> IS NOT NULL AND <col> <> ''` so blank rows coexist. A would-be duplicate insert now fails loudly with `IntegrityError`. **Keyless vehicles (blank VIN/plate/unit) are NOT covered by these indexes** (their key columns are excluded by the `<> ''` predicate), so keyless duplicate prevention relies solely on the app-level `(company, titular, model, year)` fallback in `find_duplicate_equipment` and the matching keyless signature in `dedup`.

**Idempotent bulk import (no duplicates):** `import_issues()` (`issues/routes.py`) is safe to re-run on the same file. Each row's identity is `(equipment_id, category, normalized description, canonical report day)` — severity/status are excluded so corrections re-apply instead of duplicating. The day component is the row's **parsed** date (`_coerce_date(reported_raw)`, a `date` or `None`) — NOT the stored `reported_at`, which falls back to `datetime.utcnow()` for display when the date is blank. Keying on the parsed date is critical: rows with a blank/unparseable "Fecha Reporte" key on `None` and collapse on re-import, instead of minting a fresh duplicate each run (the previous bug — the `utcnow()` fallback gave the same dateless row a different date every import, defeating dedup at both the import and `flask dedup` layers). `find_duplicate_issue(equipment_id, category, description, report_day)` derives the existing issue's day via `_canonical_report_day()` (midnight ⇒ real date; non-midnight ⇒ `None`), so a dateless new row matches a prior dateless issue regardless of its stored timestamp. Before inserting, it checks both an in-batch `seen` map (duplicate rows in the same file) and the DB via `find_duplicate_issue()` (rows from a prior import). On a match it does NOT create a new `Issue`; it updates the existing one's severity and (only if the status changed) re-runs `synthesize_status_history`. The results page reports imported / duplicates-skipped / errored counts. Driver reports are never a duplicate source (each row is distinct, live-timestamped data — even when a driver submits several problems in one POST). `flask dedup` cleans up pre-existing import duplicates by the same key (keeps lowest id; child `IssueStatusHistory` cascade-deletes). No hard DB unique constraint exists for issues — a legitimate same-day re-report of the same fault (with a real date) is valid data, so enforcement is deliberately at the import/dedup layer only.

## Static Assets

- `static/css/style.css` — All CSS in one file (~2500 lines). Custom CSS with CSS variables, no framework. **The design system deliberately matches the sibling Inventory app** (`~/Projects/Inventory`): zinc/stone neutrals (near-black `#0a0a0b` dark canvas / warm `#f7f7f5` light), a single red brand accent (`--color-lb` = `#e02020` dark / `#c81e1e` light, aliased by `--accent`; `--accent2` hover, `--glow`, `--focus-ring` per-theme), self-hosted **Geist + Geist Mono** `@font-face` at the top of the file (`static/fonts/*.woff2`, latin + latin-ext — no Google Fonts links in `base.html`), uppercase mono micro-labels (`0.62rem`, `letter-spacing 0.12em` — table `th`, form labels, `.stat-tile__label`, `.nav-section-title`, card headers), translucent status pills (10% `rgba` fill / ~25% `color-mix` border / solid text — the `-bg` tokens ARE the 10% tints now, both themes), radius ladder 6/8/12 (+16px modals, 20px pills), red-glow `.btn-primary`, active nav = accent tint + 3px left border, company panel headers = neutral `--bg-tertiary` band + 3px brand-colored left edge (no more white-on-brand fills), stat tiles with 135° sheen `::before`, staggered `fadeUp` entrances (reduced-motion gated). ALL color values live in the two `[data-theme]` blocks — keep zero hardcoded hexes in component rules. Three responsive breakpoints (1024px, 768px, 480px). Dual theme (light/dark) via `data-theme` attribute. Issue UI: severity-accented `.issue-row*` (queue) and `.issue-hero*` (detail) blocks reuse the severity/status color tokens. **Manual-entry chrome (bottom of the file):** `.created-strip` / `.created-strip-label` / `.created-strip-items` / `.created-chip` (+ `.created-chip-id`) — the "Agregados en esta sesión" trail on `manual_new.html`, a 20px-pill chip row on the existing `--bg-tertiary` + `--border-color` recipe; and `.form-shortcut-hint` (+ its `kbd`), the Ctrl+Enter caption, which is `display:none` under `@media (hover: none) and (pointer: coarse)` since touch devices have no such shortcut. `.truck-links` (beside `.truck-edit-link` in the queue block) is the flex row holding a truck card's per-truck action links; it carries the indent `margin-left` and zeroes the children's. Generic card primitives `.card-header` / `.card-body` (the `.card-header` selector shares the rule with `.profile-card-header`: uppercase banded header) style the `.profile-card`s on `issues/detail.html` and the `queue.html` Sin-unidad/Cerrados sections — keep new cards on these classes rather than re-declaring padding. Use `.card-stack` (`margin-top: var(--space-lg)`) to space stacked cards instead of inline styles. **Prev/next chrome (in the `.detail-page` block, right after `.back-link`):** `.detail-topbar` (the back-link ↔ nav flex row), `.detail-nav` (the widget), `.detail-nav-btn` (+ `.is-disabled` at 0.4 opacity / `pointer-events: none` for the first/last record), `.detail-nav-name` (the sibling's name, ellipsized at `max-width: 200px`) and `.detail-nav-count` (the mono `N de M` link back to the list) — all on existing tokens, no new ones. All **detail/profile pages share the `.detail-header` header pattern** (a `.detail-topbar` flex row — back-link left, the `.detail-nav` prev/next widget right — above an `<h1>`, optional `.detail-title-row` with right-aligned `.detail-actions`); `issues/detail.html` follows it too, with the status/severity badges shown once in the `.issue-hero` (not duplicated in the header). **Kicker headers (Inventory pattern):** list/tool pages use `.page-titlebar` — a flex row with `.page-title` (mono uppercase 0.68rem kicker + `<strong>` 1.1rem title block) left and `.page-actions` right (queue `Taller/…`, archive `Registros/Archivo`, admin `Administración/…`, import+reports `Herramientas/…`) — **except the dashboard, which deliberately has none** (see the Dashboard sorting & filtering note); the rule set is still live for those five pages, so don't prune it (nor `.page-titlebar` from the fadeUp stagger). Detail pages keep their big `<h1>` and instead get a `.page-kicker` micro-caps line above it (`Empleado`/`Equipo`/`Taller`). **Toolbar primitives:** `.toolbar` (flat flex filter row), `.search-wrap` (icon-inside search input; the class sits on the `<form>` itself), `.toolbar select` (36px Inventory input recipe), `.spacer` (`flex:1`), `.toolbar .filter-form { display: contents }`. **Sortable tables:** `th[data-sort]` + `.sort-arrow` styles live in the `.data-table` block; behavior in `app.js` `initSortableTables()`. **fadeUp stagger** is centralized in one rule set (with the `prefers-reduced-motion` kill-switch listing the same selectors): `.page-titlebar`/`.stat-tiles` at 0s → `.toolbar`/`.issue-status-tabs` at 0.1s → `.company-panels`/`.users-table-container` at 0.2s. Empty states use the Inventory look: `.empty-state` = 5rem centered padding, 2.5rem icon at opacity 0.2. `--row-hover` (`:root` alias of `--bg-hover`) is the table row hover token.
- **Design tokens (`:root`, lines ~7–140):** status color families `--color-{valid,expiring,expired,missing}` each with `-bg`/`-text` pairs (dark-theme overrides in the `[data-theme="dark"]` block). `--accent`/`--accent-bg` (alias to the LB brand red) and `--border` (alias to `--border-color`) exist **because the Issues module references them** — they were previously undefined, which rendered `.status-tab.active`, `.truck-issue-count`, and `.issue-card` borders colorless; keep them defined. Severity is tokenized as `--color-sev-{baja,media,alta,critica}` (+ `-bg`/`-text`, dark overrides), consumed by `.severity-*` (badges) and `.issue-row--*`/`.issue-hero--*` (left-border accents) — do NOT reintroduce hardcoded severity hex.
- **Data-emphasis components (readability layer):** (1) `.data-highlight` + `.data-highlight--{valid,expiring_soon,expired,missing,na}` — an outlined, status-tinted mono box (with an optional `.dh-label` caption) used to make the **permit expiration date** the focal value on every permit card (`employee.html`, `equipment.html` incl. shared-insurance card, and the `dashboard.html` company view); wrap it in `.permit-field--highlight`. The variant suffix is just `permit.status`, so it's a direct template substitution. Also used for the driver's-license date on `employee.html`. (2) `.stat-tiles`/`.stat-tile` — a KPI row used in **two** places with the same big-tile look, with two color families: the **dashboard** (`--expired`/`--expiring`/`--valid`, above the panels on **all three** dashboard views — Empleados, Equipos, **and Empresa**. Since the "Alertas" sidebar section was removed, these tiles are now the sole permit-alert surface) and the **issues queue** (`--baja`/`--media`/`--alta`/`--critica` via the `--color-sev-*` tokens + a neutral `--valid` "Todas" total tile; counts from the route's `severity_counts` — see the Severity ticker tiles note). Reusing the identical `.stat-tile*` classes on both pages is deliberate — it's what keeps the tile look consistent app-wide. **All tile rows are pressable filters, but two mechanisms coexist:** the queue AND the dashboard's Empleados/Equipos views use `<a>` tiles (server-side `?severity=` / `?permit_status=expired|expiring` filters; counts from the route — `severity_counts` / `tile_counts`; active tile gets `.stat-tile--active` and its link toggles the filter off; the neutral total tile clears it; on the dashboard the tiles sit in a `.queue-toolbar` above the sort/company/permit-type `.filter-form` selects — see the Dashboard sorting & filtering note). Only the **Empresa** view keeps the old client-side mechanism: counts via a Jinja `namespace` over each `CompanyPermit.status` (third tile labeled "Permisos"), `<button data-permit-filter="expired|expiring|all">` tiles driving a self-contained script in `dashboard.html` (wrapped in `{% if view == 'company' %}`, card selector `.permit-card[data-expired]` — `.entity-card`s no longer carry `data-expired`/`data-expiring`). The script shows/hides permit cards (each carries `data-expired`/`data-expiring` as 0/1 from its own `status`), hides any `.company-panel` left with no visible cards, and toggles `.stat-tile--active`; the "total" tile and re-clicking the active tile both clear it. This client-side filtering does NOT persist in the URL or across reloads (unlike the anchor tiles). Interactive tiles are styled by the shared `a.stat-tile, button.stat-tile` rule (`button.stat-tile` gets `font: inherit`/full-width reset so it matches the div/anchor tiles) plus `.stat-tile--active` (accent ring). (3) `.status-pill` (+ `--expired`/`--expiring`/`--missing`/`--valid`) — replaces the old tooltip-only `.status-dot` in `.entity-card` rows with a visible, touch-friendly count badge (`--valid` is a compact check circle). `.status-dot` still exists but is no longer used by the dashboard rows.
- `static/js/app.js` — All JS in one file (~210 lines). Vanilla JS, no framework. Theme toggle, sidebar/drawer (desktop collapse via `html.sidebar-collapsed` + `localStorage['sidebar-collapsed']`), flash messages, swipe gestures, and **`initSortableTables()`** — client-side click-to-sort for any `table.data-table` with `th[data-sort]` headers containing a `<span class="sort-arrow">↕</span>` (arrows cycle ↕→↑→↓, active arrow accent-colored via `.sort-asc`/`.sort-desc`; `data-sort-type="date"` parses `mm/dd/yyyy` cells, `—` sorts to the ends; rows with a trailing `.inline-edit-cell` row are grouped so the edit form travels with its parent — used by `admin_users.html`), and **`initDetailNavKeys()`** — binds ← / → to the `data-prev-url`/`data-next-url` on a page's `.detail-nav` (no-op when absent; ignored while a text control is focused or any modifier is held, so browser back/forward still work). (The alerts modal was removed along with the "Alertas" sidebar section — the dashboard stat tiles are the alert surface now.)
- `static/manifest.json` — PWA manifest with explicit `scope: "/"`. Also served at `/manifest.json` via Flask route.
- `static/sw.js` — Service worker (`CACHE_NAME` = `pt-v7`; bump it whenever cached shell assets change). Caches CSS, JS, the two latin Geist woff2 files, and Font Awesome on install. Cache-first for `/static/` and CDN assets, network-first with cache fallback for HTML.
- `static/fonts/` — Self-hosted Geist/Geist Mono woff2 (copied from the Inventory app). PWA theme-color hexes live in three places that must stay in sync: `base.html` meta tags, `app.js` `setTheme()`, and `manifest.json` (`#c81e1e` light / `#0a0a0b` dark).
- `static/img/` — Company logos (`logo-lb.png`, `logo-pli.png`) and PWA icons (`icon-152.png`, `icon-180.png`, `icon-192.png`, `icon-512.png`, `icon-maskable-512.png`).
- No build pipeline — assets served directly by Flask. `flask-compress` handles gzip/brotli. `versioned_static()` appends `?v=<hash>` for cache busting.

## Deployment

Deployed on Railway using Dockerfile. WeasyPrint requires system-level libraries (pango, cairo, gdk-pixbuf) installed in the Docker image via `apt-get`. Gunicorn runs with `--preload` for single-instance APScheduler.
